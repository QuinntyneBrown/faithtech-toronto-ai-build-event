# L2 - Detailed Requirements

## Reading conventions

[L1.md](L1.md) defines the scope, defaults, ID lineage, and ATDD conventions. Each L2 traces to exactly one L1. Retained requirement IDs have revised acceptance criteria; old tests require review against these criteria rather than an assumption that an unchanged ID means unchanged behavior.

**Actors:** a viewer can see the current public screen; an entered participant has one durable roster identity and a private browser entry session; an administrator has a server-authorized session established by the shared passcode; a database operator has independently granted database access. Merely knowing an email is not proof of ownership. All public views are suitable for projection.

**Universal acceptance:** L2-034–L2-037 apply to every screen, form, dialog, and loading/empty/success/error state. L2-038–L2-042 apply to every corresponding read and mutation over HTTP or SignalR. Connected updates must render within two seconds of durable commit. Reconnecting clients must render within two seconds after successful authoritative synchronization; unavailable synchronization must remain visibly unavailable. No screen relies on the run sheet's browser-local clock.

## L2-002: Manage participants on Countdown
**Traces to:** L1-001

Countdown must expose an administrator-only roster with email, name/public label, optional answers, team, and raffle status, plus inline add/edit/delete controls. Add requires a unique valid email and immediately enters that participant into the raffle. Updates preserve stable participant identity. Delete requires confirmation, removes personal data and membership, revokes the entry session, and excludes that participant from future grouping/draws. A completed draw retains its nonpersonal draw ID/time and a “Removed participant” result in place of deleted personal labels. Delete does not undo the draw or trigger a new one.

**Acceptance Criteria:**
1. Given an administrator on Countdown, when they add an email-only participant, then the roster count increases once and the participant is raffle-eligible without submitting a profile or signing in separately.
2. Given a saved participant, when the administrator updates email/name/answers, then a refresh shows the changes with the same identity, team, and prior-win status; a duplicate email is rejected without partial changes.
3. Given a participant with membership and a prior draw, when deletion is confirmed, then the roster and team omit that participant, their session fails, personal information is removed from subsequent responses, and the draw remains with “Removed participant”; cancelling deletion changes nothing.
4. Given an empty roster or failed save, when Countdown renders, then the administrator sees an empty message or actionable error; rejected edits retain their entered values without claiming success.
5. Given the public screen has advanced, when an administrator locally revisits Countdown, then roster management remains available without changing the public screen; an added participant appears as unassigned if teams have already formed.

## L2-003: Email entry and raffle confirmation
**Traces to:** L1-002

Public entry on Countdown must require only a syntactically valid email. Trim surrounding whitespace and compare the full address case-insensitively; do not remove dots or plus-tags. One normalized email must create at most one roster identity and one raffle entry. Saving optional details is a separate action after entry. Each participant must receive a stable public label such as “Participant 014”; a supplied name is displayed with that label to distinguish duplicate names without exposing email.

**Acceptance Criteria:**
1. Given Countdown is current and an unused valid email, when submitted, then entry and raffle eligibility are saved atomically, “You have been entered into the raffle” and the public label appear, and the optional personal-information section is offered.
2. Given simultaneous or repeated submissions of the same normalized email, when processed, then only one participant/raffle entry exists; a retry from the creating entry session restores its result.
3. Given an existing email submitted without its entry session, when processed, then the response states “This email is already entered; ask an administrator to update your details”, exposes no saved personal fields or public label, and grants no profile-editing session.
4. Given an invalid/blank email or persistence failure, when entry is attempted, then field validation or a retryable error appears, no raffle confirmation is shown, and no partial participant is committed.
5. Given entry races with Countdown closing, when the server serializes the operations, then only entry committed before closure succeeds; later public entry is rejected with “Entry is closed; ask an administrator for help”.

## L2-004: Private entry continuity
**Traces to:** L1-002

A successful new entry must establish an unguessable private browser session lasting eight hours from creation. It authorizes only that participant's saved optional information and own public label. Refresh retains entry; another browser's email submission does not recover it. A “Clear my session” action must revoke the session and clear private client state without deleting raffle entry. Lost/expired entry sessions use administrator-assisted corrections, not email-based profile recovery.

**Acceptance Criteria:**
1. Given a valid entry session, when the browser refreshes, then its participant identity and saved optional fields are restored while the main view follows the current public screen.
2. Given another or no entry session, when a participant ID is substituted in a private read/update request, then access is denied without exposing that participant's saved fields.
3. Given the session is cleared, deleted, or reaches its eight-hour expiry, when a private request or browser history restoration occurs, then private fields/drafts are cleared and protected access fails while public event viewing remains available.

## L2-005: Countdown, welcome, and brief event information
**Traces to:** L1-003

Countdown must show the event title, welcome, September 9, 2026, 5:00–9:00 PM America/Toronto, and Stone Church — Davenport Community Campus, 45 Davenport Rd, Toronto, as supplied by the run sheet. Brief copy must explain email raffle entry and the evening's team build/demo purpose. Initial countdown target is the 17:20 welcome (21:20 UTC), a specification default distinct from 17:00 doors. Deployment configuration supplies this target and copy without adding a configuration screen. Countdown uses server time, includes days when needed, and never falls below zero.

**Acceptance Criteria:**
1. Given an unregistered viewer and the configured target 90 seconds away, when Countdown opens, then welcome, brief information, email form, and a decreasing 90-second countdown are visible without login; a device clock offset of ten minutes does not change the remaining time by more than one second after synchronization.
2. Given time reaches or passes the target, when Countdown renders, then it shows zero and waits for the administrator; it neither closes entry nor advances automatically.
3. Given the target is more than 24 hours away, when displayed, then days and remaining hours/minutes/seconds are represented without wrapping the total into a misleading single day.
4. Given time synchronization is unavailable, when the screen opens or reconnects, then the target and a synchronization warning remain visible without claiming the countdown is current or showing a false successful entry.

## L2-007: Exactly four screens and manual progression
**Traces to:** L1-004

The server must persist one current screen, initially Countdown. An administrator must explicitly advance Countdown → Projects → Team selection → Raffle. Countdown's action must clearly close public entry and open Projects. Other advances must identify their destination. Public clients must follow the current screen; deep links/refresh/back cannot open a future stage or regress the event. Administrators can browse any already-opened screen locally for corrections and return to the live screen; local browsing never broadcasts a transition. Login, profile editing, roster/project editing, and feedback are inline or overlays, not extra screens. There is no global back/reset or automatic timed progression in this scope.

**Acceptance Criteria:**
1. Given Countdown and an administrator, when “Close countdown and open Projects” succeeds, then connected public browsers show Projects within two seconds and public registration closes in the same commit.
2. Given Projects then Team selection, when the respective advance action succeeds, then all public viewers advance to Team selection then Raffle; opening Raffle alone does not draw a winner.
3. Given two administrators advancing the same screen version concurrently or retrying a lost response, when requests complete, then exactly one transition occurs and no screen is skipped.
4. Given a new, refreshed, or restored public browser using any old/future deep link, when synchronized, then it shows the saved current screen without replaying earlier transitions or changing server state.
5. Given an administrator browsing a previously opened screen, when public state updates, then the local screen remains available with a current-screen indicator and “Return to live” action; public browsers continue following the server.
6. Given the run-sheet times for projects (17:50), teams (18:05), or raffle (20:50) pass, when no administrator advances, then the current screen remains unchanged; PowerPoint requires no connection to this application.

## L2-009: Administrator member rearrangement
**Traces to:** L1-005

Team selection must display labeled team groups and an unassigned area. Administrators must move members between teams or from unassigned using drag and drop, with an equivalent keyboard/touch “Move to team” control. Moving to “New team” creates a group; moving to “Unassigned” removes membership. Manual corrections can exceed three members or produce pairs. Empty teams remain visible for reassignment and retain their selected project; no team deletion feature is required.

**Acceptance Criteria:**
1. Given a participant in team A, when an administrator drops them on B or selects B using the equivalent control, then membership changes atomically from A to B and all connected team views reflect that single membership within two seconds.
2. Given an unassigned participant, when moved to an existing or new team, then they appear there once; a new team receives a distinct public team label and no project.
3. Given a full three-person team or the run sheet's eight-person turnout, when an administrator rearranges members, then a fourth member or four pairs respectively can be saved without automatic rebalancing.
4. Given a failed/stale move or a cancelled drag, when the outcome displays, then the confirmed team memberships remain authoritative, no member disappears or duplicates, and a rejected move explains how to retry.
5. Given a move from a team with project P to one with Q, when committed, then each team's project stays with that team and the moved participant sees Q; ordinary participants cannot move themselves through UI or direct requests.

## L2-010: Form random teams once on first opening
**Traces to:** L1-005

The first successful global transition from Projects to Team selection must uniformly shuffle all currently entered, nondeleted participants and partition them into teams of three, with one final team of one or two for any remainder. No attendee is omitted, duplicated, or inferred from the run sheet's registration count. Optional answers do not influence selection. Team identities/memberships and the opened stage must commit together once. Later page loads, reconnects, and additional viewers must never reshuffle. Later administrator-added participants remain unassigned until an explicit move.

**Acceptance Criteria:**
1. Given 0, 1, 2, 3, 4, 8, or 13 entered participants, when Team selection first opens, then team sizes are respectively [], [1], [2], [3], [3,1], [3,3,2], or [3,3,3,3,1], and each entered identity appears exactly once; zero participants shows an explicit empty state.
2. Given different controlled shuffle outcomes in API integration fixtures, when teams form from the same roster, then assignments follow each outcome without weighting by name, email, profile answers, or insertion order.
3. Given simultaneous first-opening requests or a successful transition with a lost response, when requests complete or retry, then only one saved grouping exists and every browser receives it unchanged.
4. Given storage failure during formation, when transition fails, then Projects remains current with no partial teams; a successful retry forms one complete grouping.
5. Given teams have formed and members have been manually rearranged, when another viewer opens Team selection or the service restarts, then saved corrections remain and no new shuffle occurs.

## L2-011: RTR project cards and team project assignment
**Traces to:** L1-005

Projects must show a card for each saved project with title, plain-text description, and optional supplied repository/demo HTTPS links. The initial catalogue must include “RTR — Reconciliation Through Relationships” with a brief description drawn from the run sheet. Its project-specific workflows are descriptive content, never new companion features. The run sheet gives no repository/demo URL or guest-project details; absent links are omitted and no fictional guest card is seeded. Administrators assign, replace, or clear one project per team on Team selection. Multiple teams can share a project; participants cannot select or propose projects.

**Acceptance Criteria:**
1. Given the initial catalogue, when Projects opens, then the RTR card describes the relationship/learning/matching project from the run sheet without inventing a repository or demo address; missing links do not block viewing.
2. Given saved project cards, when a viewer uses a supplied link, then it opens the validated target; an empty catalogue shows “No projects added yet” and the administrator has an add action.
3. Given a team and existing project, when an administrator assigns or changes it, then that team's members and connected viewers see the selected project within two seconds without changing memberships or other teams' assignments.
4. Given two teams, when both are assigned the same project, then both succeed; clearing one leaves the other assigned, and selecting a nonexistent/deleted project fails without clearing the saved selection.

## L2-012: Manage projects on Projects
**Traces to:** L1-005

Administrators must add, update, and remove projects through forms on Projects, including when locally revisiting it. Title and description are required; repository and demo links are optional. Removal must identify the project and its assigned teams in a confirmation. Confirming removal must atomically delete the project and clear those teams' project assignments while preserving all memberships. Initial catalogue provisioning must not restore deleted projects on restart.

**Acceptance Criteria:**
1. Given an administrator on Projects, when a valid project is added or edited, then connected project cards and assigned-team descriptions reflect the saved content within two seconds and refresh preserves it.
2. Given blank required fields, invalid links, or a failed save, when submitted, then field-specific/retry feedback preserves the draft and the saved catalogue remains unchanged.
3. Given a project assigned to two teams, when removal is confirmed, then its card disappears and both teams show “No project assigned” with their members intact; cancelling leaves all data unchanged.
4. Given a removed project, when the API restarts and Projects reloads, then it stays removed; participant attempts to add/edit/delete are denied by the server.

## L2-013: Optional introduction information
**Traces to:** L1-006

After successful email entry on Countdown, the participant must be offered optional Name, “What you make”, and “What's on your heart” fields with Save and Skip actions. A short notice must explain that a name/public label appears on teams and raffle results, while email and the two answers are visible only to the participant's authorized entry session and administrators. Saving answers does not change raffle odds or grouping. The owner can edit while Countdown remains public; after closure, corrections are administrator-only.

**Acceptance Criteria:**
1. Given a newly entered participant, when Skip is chosen or every optional field is blank, then raffle eligibility remains and no additional information is required to view subsequent screens.
2. Given the valid entry session, when any subset of fields is saved and refreshed before closure, then supplied values return; clearing a field removes its saved value and clearing Name restores the stable public label.
3. Given an invalid/failed optional save, when feedback displays, then the accepted email entry remains raffle-eligible, the draft is retained, and no message suggests the raffle entry failed.
4. Given a different participant or public viewer, when team/raffle payloads or private profile endpoints are requested, then email and optional answers are absent or access is denied; the administrator can read them on Countdown.
5. Given an unsaved optional draft when Countdown closes, when the transition arrives, then Projects opens with notice that unsaved details were not submitted; the draft is discarded and the already-confirmed raffle entry remains valid.

## L2-020: Raffle pool and public results
**Traces to:** L1-008

Raffle must display the eligible count, latest result, and previous winners within that same screen. Every nondeleted entered participant, including administrator-added participants, has one chance per draw until winning. Previous winners are excluded from later draws, including after email/name edits. Names are displayed with stable public labels; unnamed entrants use their public label alone. There is no prize-selection prerequisite or prize catalogue. Deletion removes an identity from future participation; registering an email again through the administrator creates a new identity rather than recovering a deleted profile. This email-only scheme does not verify a natural person's identity or prevent entry under multiple different emails.

**Acceptance Criteria:**
1. Given entered A and B, deleted C, and previous winner D, when eligibility is computed, then only A and B are eligible, irrespective of optional fields, team, or project.
2. Given two matching names or no names, when the raffle displays candidates/results, then stable public labels distinguish identities without exposing emails.
3. Given no eligible entrants, when Raffle opens or a draw is attempted, then “No eligible participants” appears, DRAW NAME is disabled for administrators, and a direct draw request creates no result.
4. Given an existing winner renamed or given a different email, when another draw occurs, then that same identity remains excluded; a public viewer sees result labels but never the private roster.

## L2-021: Fair, durable, single-result draw
**Traces to:** L1-008

Only an administrator on the live Raffle stage must be able to start a draw using **DRAW NAME**. The server must select uniformly among current eligible identities using cryptographically secure randomness and persist winner, draw ID, candidate-label snapshot, server start/reveal times, and exclusion before animation. Only one draw can run at a time. Requests must include the observed raffle version and an operation identity so concurrent clicks, delayed clicks, and retries do not consume extra winners. The result is final; there is no redraw/undo feature. Public changes to a selected winner's name or deletion follow current privacy rules even for retained snapshots.

**Acceptance Criteria:**
1. Given one eligible participant, when DRAW NAME succeeds, then that participant wins once and is excluded from subsequent draws; a controlled-randomness integration fixture can select each identity in a fresh multi-person pool.
2. Given concurrent requests from two administrators using the same raffle version, when processed, then exactly one draw is persisted; the other returns a conflict or that same outcome, never a second winner.
3. Given a committed draw with a lost response, when retried with its operation identity, then the same draw/result returns even after animation ends; changing the payload under that identity is rejected.
4. Given a draw in progress or a stale request delivered after it completes, when submitted, then no second draw starts; a deliberate later draw requires the current version and a new operation identity.
5. Given a deletion races with a draw, when serialized, then deletion first excludes the participant; draw first preserves that result with the later deletion replacing personal labels by “Removed participant”.
6. Given durable storage fails, when a draw cannot commit, then no winner is announced, no participant is excluded, and DRAW NAME becomes retryable with an error.

## L2-022: Animated name cycling and WebGPU celebration
**Traces to:** L1-008

After the server commits a draw, connected Raffle views must cycle its candidate display labels, decelerate, and settle on the persisted winner at the server-defined reveal time, five seconds after draw start. Falling confetti-like particles must celebrate for at most five further seconds using a Cornerstone WebGPU effect where available. Controls and text remain usable; the winner remains visible after effects stop. The reveal timestamp coordinates presentation, not a secrecy guarantee against inspecting a committed result in network traffic. No sound is required.

**Acceptance Criteria:**
1. Given WebGPU is available and reduced motion is off, when a committed draw arrives, then candidate labels cycle, slow, settle on the saved winner within one second of the reveal time on synchronized foreground clients, and falling particles stop within five seconds afterward.
2. Given late arrival/reconnection during an active draw, when state synchronizes, then the view joins the remaining timeline rather than restarting five seconds; after reveal it shows the winner immediately without replaying effects.
3. Given unavailable/denied WebGPU or device loss during celebration, when presentation runs, then a lightweight Cornerstone fallback reveals the same winner by the same deadline, releases failed GPU resources, and leaves later draws usable.
4. Given reduced motion is enabled before or during a draw, when it is presented, then rapid cycling and particles are omitted/stopped, static “Drawing…” remains until reveal, and the same winner appears as accessible text.
5. Given animation rendering fails entirely, when the result arrives, then accessible text still exposes the committed winner by reveal time and no animation failure invokes another draw.

## L2-029: Consume the published Cornerstone UI
**Traces to:** L1-011

All rendered application UI must be composed from `@quinntyne/cornerstone` npm components and styles, including forms, buttons, cards, tables/lists, dialogs, countdown presentation, team-board interactions, validation/status UI, and raffle animation/effects. Application code supplies data, actions, and screen composition. A clean install must resolve a pinned released package version through the lockfile without a local Cornerstone checkout. Existing local control implementations are not an alternative delivery path.

**Acceptance Criteria:**
1. Given a clean checkout and access to its declared npm dependencies, when the app is built and its four screens exercised without a Cornerstone checkout, then all public/admin controls and visual effects render and operate using the adopted release.
2. Given the same supported inputs and states, when a Cornerstone control is exercised in its published examples and the app, then its focus, validation, disabled, loading, and interaction behavior remains consistent; review records package version and component provenance without adding structure-scanning tests.

## L2-030: Package-owned tokens and styling
**Traces to:** L1-011

Cornerstone must be the authoritative source of colour, spacing, dimensions, typography, borders, radii, shadows, icons, and motion tokens. Application composition must consume package tokens and supported styling APIs. Missing tokens must be added upstream; no locally mirrored token catalogue, copied stylesheet, hard-coded visual replacement, or independent design-system site satisfies this requirement.

**Acceptance Criteria:**

2. Given a missing visual role is added and released in Cornerstone, when the application adopts the new version, then the affected composition renders the new role without a local token copy or component-specific replacement; this ownership constraint is verified by review.

## L2-033: Complete missing UI in Cornerstone first
**Traces to:** L1-011

For each missing component, behavior, token, or accessibility capability, implementation must extend Cornerstone with its own behavioral coverage and examples, release `@quinntyne/cornerstone` to npm, then update and verify the app against that released version. This includes drag-and-drop with an accessible alternative and WebGPU/fallback raffle presentation if absent. Local source aliases, copied primitives, unpublished workspace links, or another UI library cannot satisfy completion. Package availability and APIs must be inspected during implementation; this specification makes no claim that the necessary capabilities already exist.

**Acceptance Criteria:**
1. Given a required interaction absent from the current release, when the feature is accepted, then the published upgraded Cornerstone example and the application's corresponding user journey both perform the required interaction successfully.
2. Given a clean app checkout without the upstream repository, when dependencies are installed from the updated lockfile and the relevant acceptance journey runs, then the feature works from the npm release alone.
3. Given an upstream release cannot yet be consumed, when delivery status is reported, then the feature remains incomplete rather than being reported complete on the strength of a local replacement; upstream version/provenance checks are review evidence, not architecture tests.

## L2-036: Keyboard, semantics, and feedback
**Traces to:** L1-012

All controls must have accessible names, visible focus, and keyboard operation. Dialogs must contain focus and restore it to their trigger or current heading if the trigger is gone. Validation must preserve entered values and associate/announce field errors. Stage changes and winner results must be announced once; countdown ticks and cycling names must not create repeated screen-reader announcements. Text contrast must reach 4.5:1, or 3:1 for large text; meaningful control boundaries/focus indicators must reach 3:1. Fix missing accessibility upstream in Cornerstone.

**Acceptance Criteria:**
1. Given keyboard-only input, when a user completes email entry, optional fields, passcode login, roster/project CRUD, team moves, project assignment, and draw, then each action is possible without dragging or pointing.
2. Given a failed form submission or dismissed dialog, when feedback appears or focus returns, then the affected fields are announced and values retained, or focus returns to the trigger/current heading respectively.
3. Given a screen change or raffle reveal, when the UI updates, then the new heading/result is announced once and focus moves to the heading only if its previous element was removed; ticking/cycling labels do not flood announcements.
4. Given supported light-theme states, when contrast and focus are inspected, then they meet the stated thresholds, including disabled-status explanations and keyboard move controls.

## L2-037: Reduced motion and resilient presentation
**Traces to:** L1-012

The app must honor reduced-motion preferences throughout. Essential meaning must also appear in text rather than colour or movement alone. Long animations must offer a stop-effects control within Raffle without affecting the selected winner. No audio feature, permission prompt, or mute UI is required.

**Acceptance Criteria:**

2. Given a viewer stops raffle effects, when the action completes, then visual motion stops, the saved result still appears at reveal, and other viewers' draws/results are unchanged.
3. Given colour is not perceived or effects fail, when a team move or winner is shown, then labels and status text communicate the same outcome.

## L2-038: Shared four-digit administrator login
**Traces to:** L1-013

An Admin action must open an inline Cornerstone login panel/dialog from any current screen. Login requires exactly four ASCII digits, including leading zeros, and no username or participant entry. A successful login enables the administrator's controls only in that browser session. The server must validate authority for every privileged read/mutation and SignalR subscription/action. Administrator sessions expire at 30 minutes without explicit user interaction or eight hours after login, whichever occurs first; background updates do not renew activity. Logout returns to the live public screen and clears privileged drafts/data. There is no production default passcode or public setup route.

**Acceptance Criteria:**
1. Given a provisioned passcode of “0042”, when those four digits are submitted, then the same app shows administrator controls; “42”, letters, extra digits, whitespace, and incorrect four-digit values do not authenticate.
2. Given a participant or anonymous browser, when an administrator request or privileged SignalR subscription is made directly or a client-side admin flag is altered, then the server denies it without exposing the roster or changing state.
3. Given two browsers and a successful admin login in one, when state broadcasts, then only that browser receives admin privileges and privileged fields; the other remains a public viewer.
4. Given logout, passcode replacement, 30 minutes without explicit interaction, or eight hours since login, when a privileged operation is attempted, then it fails and privileged client state is cleared; background updates do not prevent expiry.
5. Given no valid provisioned passcode, when login is attempted, then no guess/default grants access and operators receive a redacted configuration error; public viewing remains available if event data is otherwise ready.

## L2-039: Public and private data boundaries
**Traces to:** L1-013

Public HTTP/SignalR responses must contain only event copy, projects, team public labels/memberships, and public raffle state. Participant email and optional answers are visible only to that participant's valid entry session and administrators. Full roster access is administrator-only; administrator capability must not be inferred from public group membership. Name/public-label display must be explained before entry/profile save. Public responses must exclude passcodes, verifiers, session identifiers, and internal failure details.

**Acceptance Criteria:**
1. Given synthetic private email/answer values, when public endpoints, team/project views, and raffle snapshots/messages are inspected, then those values are absent; authorized private reads return only the permitted participant or administrator data.
2. Given an unauthorized viewer knows a participant ID or SignalR group name, when they request/join it, then private information is not disclosed.
3. Given an administrator session expires or a participant is deleted, when its connected private view receives invalidation, then it clears within two seconds; reconnect must reauthorize before loading private content.
4. Given public entry, when the form is shown before submission, then it explains raffle enrollment, public name/label use, and the privacy of email/optional answers in brief readable text.

## L2-040: Validate text, emails, and links
**Traces to:** L1-013

The server must validate all inputs. Email is required, at most 254 characters, with one nonempty local part and domain separated by @, no whitespace/control characters, and a syntactically valid domain; plus-tags and subdomains are accepted. Optional name and required project title are limited to 200 characters; each optional answer and required project description to 2,000; optional repository/demo URLs to 2,048. Text is trimmed and line endings normalized to LF; limits count Unicode scalar values. Optional blank values clear a field. All free text is rendered literally, never executable HTML. URLs must be absolute HTTPS without embedded credentials. The API must never fetch submitted project URLs. No file upload feature is required.

**Acceptance Criteria:**
1. Given values at the specified limits and values one character above, when saved, then boundary values succeed and oversized values fail with field-specific errors and no partial write; required whitespace-only text fails.
2. Given valid plus-tag/subdomain addresses, when entered, then they are accepted as separate normalized addresses; missing local/domain parts, multiple @ signs, whitespace, or control characters fail.
3. Given markup, script/event-handler syntax, or SQL-like text within an allowed free-text length, when saved and rendered, then it is displayed literally without code or query execution.
4. Given HTTP, relative, credential-bearing, or executable-scheme links, when saved, then validation rejects them; blank optional links clear them, and valid HTTPS links open without control over the original page.

## L2-041: Protect credentials and browser sessions
**Traces to:** L1-013

Production must use HTTPS and Secure, HttpOnly, SameSite cookies for private entry/admin sessions, with server-side revocation and cross-site request protection. Session credentials must have at least 128 bits of cryptographic randomness. Passcodes and session secrets must not appear in URLs, logs, analytics, or script-readable persistent storage. Store the four-digit passcode as a salted nonrecoverable verifier; protect database/backups and the verifier from public reads. The short passcode has only 10,000 possible values, so rate limits and restricted verifier access remain required; hashing does not make it a high-entropy password. Direct database replacement must support this storage format without requiring the operator to use the CLI.

**Acceptance Criteria:**
1. Given successful entry/admin login in production configuration, when traffic, logs, and browser storage are inspected, then secrets are sent only over HTTPS, cookies have the required protections, and secrets do not appear in URLs or script-readable persistent storage.
2. Given an untrusted origin attempting a cookie-authenticated mutation or privileged SignalR connection, when processed, then it is rejected without data change or privileged subscription.
3. Given passcode storage and ordinary database diagnostics, when inspected, then the submitted plaintext passcode is absent; only the restricted verifier and necessary metadata persist.
4. Given logout/expiry followed by history navigation, when a privileged/private view is restored, then it does not expose cached private content and requires reauthorization.

## L2-042: Bounded abuse and retry feedback
**Traces to:** L1-013

Administrator login must allow at most five failed passcode checks per source address in a rolling five minutes and 20 across the deployment in a rolling five minutes. After either limit is exhausted, reject further checks with a positive Retry-After value until failures age out. Throttled attempts do not extend the window. Counters must survive service restart and be shared by instances. Public email submissions must be limited to 60 attempts per source per minute, with syntax/duplicate attempts included and no permanent lockout. Shared-venue IPs must support the normal event-entry burst. These limits are specification defaults and must be documented in the operator runbook.

**Acceptance Criteria:**
1. Given five failed admin checks from one address, when a sixth attempt arrives in the window even with the correct passcode, then it is throttled before verification; after the failures age out, valid login succeeds.
2. Given 20 failed checks across multiple addresses, when another attempt reaches another app instance or the service restarts, then the deployment limit still applies with retry feedback.
3. Given 60 public submissions from one address in a minute, when the 61st arrives, then it receives retry feedback without mutation; after the window expires, entry resumes if Countdown is still open.
4. Given an incorrect passcode, throttling, or expired session, when feedback appears, then it explains invalid login, retry delay, or reauthentication without exposing the correct passcode or internal details.

## L2-044: SignalR synchronization, persistence, and conflicts
**Traces to:** L1-014

SignalR must deliver screen changes, roster-derived public changes, private administrator roster changes, project edits, team updates, draws, and session invalidation to authorized connected clients. HTTP can load snapshots and submit commands, but polling alone does not satisfy realtime delivery. State must be durable before success/broadcast. Snapshots and events must carry ordering/version information so duplicate/out-of-order messages cannot regress state. Reconnect/resume must reauthorize and obtain a current snapshot. Show connection loss within ten seconds of a confirmed transport failure; while disconnected/synchronizing, disable server-changing controls and never claim fresh authority. Do not queue mutations for silent replay.

All mutations must reject stale conflicting versions. Retries retain operation identity and input, and return the original saved outcome after authorization without applying it again; changed input under that identity fails. Rejected edits retain drafts for explicit reapply, except privacy/session invalidation and the participant draft closure rule in L2-013. Initial-entry retries must retain an unguessable pre-submission operation receipt scoped to the creating browser so a lost response can recover that entry without letting knowledge of an email claim it. The receipt is a private session credential under L2-041, not a user-entered code.

**Acceptance Criteria:**
1. Given two connected public clients and an administrator, when each supported mutation commits, then applicable views update through SignalR within two seconds; public messages omit private roster data and only the administrator receives the authorized roster update.
2. Given duplicated/reordered events and a snapshot fetched concurrently with a new event, when synchronized, then the client converges on the newest saved version without regressing membership, current screen, or winner.
3. Given disconnection across several changes, when reconnection succeeds, then current screen/state replaces stale state within two seconds after the snapshot, with no replayed mutation or completed raffle animation.
4. Given two editors of the same version, when one save commits, then the other receives a conflict and authorized current values while retaining its draft for explicit reapply; no silent overwrite occurs.
5. Given a successful entry or admin mutation loses its response, when the same authorized browser retries with its original operation receipt/identity, then it receives the original outcome once; an unrelated browser submitting the email gets no ownership session.
6. Given storage fails mid-operation or the service restarts after acknowledgement, when state is reread, then respectively no partial success is visible or the entire acknowledged state remains, including grouping and draw history.

## L2-063: Replace the passcode directly through the database
**Traces to:** L1-016

The database must expose a documented, supported direct SQL operation accepting a new four-digit value and performing any necessary verifier conversion and credential-revision update atomically. An operator must be able to execute it from a normal database client without the web API, CLI, or old passcode. The database operation must reject invalid format, preserve leading zeros, and leave event/participant data unchanged. A committed different passcode must invalidate all existing administrator sessions; using the same value deliberately must also rotate the credential revision and revoke sessions. No redeploy/restart is required. Raw unsupported edits must not create a fallback/default admin credential.

**Acceptance Criteria:**
1. Given database access and the application stopped, when the documented direct SQL operation sets “0042”, then after startup only “0042” authenticates, the previous different passcode fails, and event/participant data is unchanged.
2. Given a running app with multiple admin sessions, when direct replacement commits, then every subsequent privileged request checks the new revision and rejects old sessions immediately, connected admin views clear within two seconds, and login with the new passcode succeeds without restart.
3. Given three/five digits, letters, whitespace, NULL, or a storage failure, when replacement is attempted, then neither verifier nor credential revision changes; an intentional same-value replacement revokes old sessions while retaining that login value.
4. Given two concurrent replacements, when serialized, then each is atomic and the last committed value/revision is authoritative; no instance continues to accept a previous value from a stale cache.

## L2-064: Replace the passcode through the installed CLI
**Traces to:** L1-016

The CLI must provide `set-admin-passcode` with exactly one of masked interactive input or `--passcode-stdin`, and an explicit database target. It must use the same database replacement behavior as L2-063. Empty input, EOF, cancellation, invalid format, or invalid target must never select a default. Success confirms replacement without printing the passcode. Exit codes must be 0 confirmed success, 1 confirmed operation/authentication/permission failure, 2 invalid syntax/configuration/input or cancellation before execution, and 3 unconfirmed commit/result delivery. Connection loss after execution must not be reported as confirmed rollback or trigger automatic replay; verification and any deliberate replacement are separate operator actions.

**Acceptance Criteria:**
1. Given the installed CLI and valid target/permissions, when a new four-digit passcode is entered by masked prompt or stdin, then it authenticates via the real API, the old different value and old sessions fail, and no unrelated event data changes.
2. Given missing/conflicting modes, invalid input, EOF, cancellation before execution, or denied database access, when invoked, then it exits with the specified nonsuccess class and leaves credentials unchanged without a fallback value.
3. Given a commit followed by connection loss or failed result delivery, when completion cannot be confirmed to the operator, then exit 3 explicitly reports the uncertain outcome and does not repeat the write automatically.
4. Given direct SQL replacement followed by CLI replacement and then another direct replacement, when API login is checked after each, then the latest committed value works and older sessions fail consistently through both paths.
