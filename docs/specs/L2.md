# L2 - Detailed Requirements

## Reading and verification conventions

[L1.md](L1.md) defines scope, approved defaults, and mandatory ATDD conventions. Each requirement below traces to exactly one L1. Unless stated otherwise, participant actions require an active registration in the selected event and administrator actions require the admin role. Events isolate all participant and activity data.

CLI operator actions use a separately authenticated database principal, not an application administrator session. Browser/API authentication, privacy, and event-boundary rules remain unchanged. CLI-specific criteria govern local input and output; browser viewport, cookie, and CSRF requirements do not apply to the terminal.

Validated CLI commands retain application data and lifecycle rules. Explicit operator SQL under L2-056 can inspect and repair data across events, including deletion and lifecycle corrections unavailable to browser administrators; this is a deliberate exception to ordinary application mutation restrictions, not an expansion of browser roles. The SQL path does not claim to enforce application invariants or protect data from the authorized database operator. Credential protection and redacted diagnostics still apply.

**Provenance:** Product capabilities come from [the prompt](../prompt.md) and the explicit decisions listed in L1. Numerical limits, recovery behavior, and precise boundary rules are specification defaults that make those decisions testable, not claims that those details appeared in the prompt or were individually confirmed. The [review record](REVIEW.md) identifies new defaults and corrections. Actual roster entries, credentials, content, prizes, projects, map coordinates, and venue address are administrator-supplied event data, not invented seed data; L2-008 explicitly supplies editable informational preset content only.

**Cross-cutting acceptance:** Every UI-facing requirement must also pass L2-035 through L2-037 at its relevant screen, including loading, empty, success, validation, and failure states. Every protected action must satisfy the applicable actor and operation rules in L2-038 through L2-042; participant actions do not require the admin role. Security and responsiveness criteria apply even when not repeated under a feature.

**Measurement and recovery:** Unless stated otherwise, the two-second connected-update deadline runs from the authoritative scheduled instant or durable save to the applicable client rendering/announcement. Reconnection starts authentication and synchronization immediately; after a successful synchronization response, the client must render within two seconds. A failed or pending synchronization must retain an explicit unavailable/reconnecting state, never claim fresh authority. Server authorization applies to every request immediately; a disconnected browser cannot learn a remote revocation until contact resumes. Connected clients must clear revoked private views within two seconds of receiving invalidation, and restored tabs must revalidate before exposing cached private content. Session expiry known to the browser must still clear private content while offline.

**Terminology:** An active registration is a roster entry not deactivated by an administrator. A stage is one timed screen entry; a named phase can contain several stages. The selection stage/window is one event-level interval permitting participant team/project changes, independent of which screen is current. Stage changes do not imply project progress. Event project descriptions are shared choices; an event/team/project pairing stores that team's repository/demo links. Core activities remain accessible through event navigation when a scheduled screen changes, but time-limited mutations remain governed by their server-side windows.

## L2-001: Independent event configuration

**Traces to:** L1-001

Administrators must create and edit events with a title, timezone, start/end, venue name and location, logo, participant-facing content and links, and team/project/activity settings. Incomplete configuration must be saveable as a draft; only published events admit participants. A publishable event must have a title, valid schedule, venue location, and logo.

Drafts may omit publication fields; supplied values must still satisfy syntax, size, and applicable interval validation. Publication additionally requires a venue name, a valid map-marker latitude/longitude pair, an accepted logo, and resolved event/stage instants. A textual address is optional; coordinates provide the textual fallback when absent. An empty stage list is valid and uses configurable waiting content. Administrators must edit waiting content, closing content, and an optional HTTPS directions link; absent waiting/closing text uses a neutral waiting/thank-you message without invented event details. Publishing is an explicit action, separate from draft saving; this version does not add event deletion or unpublishing.

**Acceptance Criteria:**

1. Given an administrator and two events, when content or settings are saved in one event, then reloading shows those values only in that event.
2. Given missing publication fields, when publication is requested, then field-specific errors are shown and the event remains a draft; draft saving still succeeds.
3. Given a published event, when an administrator saves valid content or link changes, then connected clients show the new values within two seconds without signing in again.
4. Given an invalid edit to a published event, when saving is attempted, then the last valid configuration remains active and the administrator sees the validation errors.
5. Given an event with no stages and valid publication fields, when it is published, then access succeeds and participants see the countdown before start, waiting content from start until end, and the recap at end.
6. Given malformed supplied URLs or a complete but overlapping stage interval, when a draft is saved, then the invalid supplied values are rejected without losing the previously saved draft.
7. Given valid waiting/closing content and directions saved by an administrator, when the corresponding participant screen opens, then it displays that event's saved values and the directions action remains independent of the map.

## L2-002: Participant roster and credentials

**Traces to:** L1-001

Administrators must add, rename, deactivate, and reactivate event roster entries and issue or replace individual entry codes. Names need not be unique; participant identity must not depend on a name. A replacement code must invalidate the prior code and sessions without deleting participation history.

Deactivation must retain identity, membership, profile, submissions, messages, reports, and awards, while immediately preventing new protected actions and removing the entry from discovery, recommendations, and raffle eligibility. Administrators must confirm deactivation or code replacement with the affected entry identified; cancellation changes nothing. Reactivation must require fresh authentication and must not restore revoked sessions. If the retained email is now bound to another active entry, reactivation must fail until the administrator explicitly clears this entry's binding through code replacement. Entry-code issuance must be unique within its event; codes must not be editable or retrievable as roster fields.

**Acceptance Criteria:**

1. Given two participants with the same name, when both are added, then each receives a distinct identity and credential and retains separate activity results.
2. Given an existing participant, when their display name changes, then their team, submissions, messages, and wins remain attached to the same identity.
3. Given a deactivated entry, when its credential or existing session is used, then event access is denied; reactivation restores access to its retained history.
4. Given a lost code or incorrect bound email, when an administrator replaces the code and explicitly clears the email binding if needed, then the old code and sessions fail and only the new code can establish access.
5. Given deactivation followed by reactivation, when the participant authenticates afresh, then retained history and membership are restored subject to current event permissions; a session revoked by deactivation still fails.
6. Given an inactive entry whose email now belongs to another active entry, when reactivation is attempted, then it is rejected without creating two active bindings; clearing the inactive binding with a replacement code permits a new unique email binding.

## L2-003: First access and email binding

**Traces to:** L1-002

The access screen must accept an email and individual entry code for the selected event. First successful access must atomically bind a trimmed, case-insensitive email to that roster entry. Each normalized email must identify at most one active roster entry per event. No email-verification or email-delivery service is required by this version.

**Acceptance Criteria:**

1. Given a published event and an unclaimed active entry, when a valid email and its code are submitted, then one binding is saved and the participant reaches the screen appropriate to the current event time.
2. Given an already bound entry, when the matching email with different casing or surrounding spaces and valid code are submitted, then access resumes as the same participant without creating another registration.
3. Given two concurrent first-access attempts using different emails for one code, when processed, then exactly one binding succeeds and the other is denied without changing the winner's binding.
4. Given a malformed email, duplicate event email, wrong-event code, revoked code, or mismatched bound email, when submitted, then access is denied without disclosing another participant's name or email; field syntax errors can identify the malformed field.

## L2-004: Session continuity and sign-out

**Traces to:** L1-002

Participant sessions must survive refresh and remain valid for 24 hours after authentication unless revoked. Participants must be able to authenticate again after the event to view its recap. Sign-out must revoke the current session and clear private client state.

The 24-hour lifetime is absolute, not extended by reads or refresh. Expiry, revocation, and sign-out must clear displayed private content and in-memory drafts for that session, including on history navigation or restored tabs; durable event history remains available after authorized reauthentication. Other valid sessions are unaffected by signing out only the current session. Switching event views must isolate drafts by event and participant. Draft retention under L2-007/L2-044 applies only while the session remains authorized.

**Acceptance Criteria:**

1. Given a valid session, when the participant refreshes or opens the event again, then the same identity and current event state are restored without code re-entry.
2. Given a signed-out, expired, or revoked session, when a protected screen or action is requested, then access requires authentication and cached private content is not displayed.
3. Given a completed event and active registration, when the participant authenticates again, then the recap opens without reopening closed team selection or quizzes.
4. Given a session authenticated 24 hours earlier and refreshed repeatedly, when its exact expiry instant is reached, then protected access fails and private content/drafts are cleared; reauthentication restores saved history but never discarded drafts.

## L2-005: Countdown and venue display

**Traces to:** L1-003

Before the configured start, authenticated participants must see the event title, venue name, configured logo, location map, textual address or coordinates, and a nonnegative days/hours/minutes/seconds countdown derived from server time. Configured external directions must remain usable independently of the embedded map.

The map must mark administrator-supplied latitude and longitude; neither an illustrative mock map nor an inferred/geocoded address constitutes saved location. Latitude must be a finite value from -90 to 90 and longitude from -180 to 180. The client may load map tiles from its configured mapping provider, but saved branding/content must not introduce arbitrary executable map embeds. Date, start/end, countdown, and displayed location must come from the selected event; the day portion must remain visible for events more than 24 hours away.

**Acceptance Criteria:**

1. Given an event starting in 90 seconds, when its countdown is viewed, then the remaining time is displayed and decreases without a page reload; changing the device clock does not change the authoritative start.
2. Given a reachable configured map and logo, when the screen loads, then the map marks the configured location and the logo has an accessible venue label.
3. Given a failed map or logo load, when the countdown renders, then the event title, textual location, available directions link, and countdown remain usable with an explanatory fallback.
4. Given a connected countdown client, when server time reaches the event start, then the live screen opens within two seconds without a participant action and the countdown never becomes negative.
5. Given an event more than 24 hours away and no textual address, when the countdown loads, then it includes days and the configured coordinates; neither the sample venue address nor another event's branding appears.

## L2-006: Schedule validation and exact boundaries

**Traces to:** L1-004

Administrators must configure event and stage start/end times, named stages, and their screen content or activity. Start is inclusive and end exclusive. Stages must have positive durations, be within the event interval, and not overlap. Event timezone and offset must resolve each scheduled instant unambiguously.

Administrators must configure a positive selection window and a positive demo-presentation interval within the event, or explicitly disable each activity. Disabled selection permits administrator assignment only. Window boundaries need not match individual screen boundaries. All scheduled values must include local dates as well as times so overnight events are unambiguous. Event, stage, and activity interval edits must be validated and saved together; a dependent invalid interval must identify its conflict without partially activating the edit. A nonexistent local time cannot be repaired by supplying an offset: it must be replaced with a valid local time; an ambiguous time requires one of its valid offsets.

Once an enabled selection window or activated quiz has reached its closing instant, it must remain closed even if nobody was connected. Before accepting a timing edit, determine closure from the previously committed schedule and authoritative time; a later closing time, disable/enable cycle, or screen reassignment cannot reopen it. Once opened, its opening instant cannot be moved to reset it. Disabling an open selection window closes it permanently. Completed events must remain completed; edits cannot extend their end to reopen participant link editing or timed activities. Valid content corrections, administrator assignment corrections, and result reads remain available. These closure facts must survive restart under L2-044.

**Acceptance Criteria:**

1. Given invalid ordering, overlapping stages, duplicate starts, or a stage outside the event interval, when saved, then the invalid schedule is rejected with the offending intervals identified.
2. Given adjacent stages A ending and B starting at 18:05, when server time reaches 18:05, then B is current; an action window ending then is closed, while an independent window spanning both stages remains open.
3. Given a gap between stages, when server time enters it, then waiting content and the next stage time appear; after the last stage but before event end, waiting content shows the event end instead of inventing a next stage.
4. Given an ambiguous time without a valid resolving offset or a nonexistent local time, when saved, then the schedule is rejected with the affected timezone field identified.
5. Given selection from 18:05 to 18:15 and screen entries starting at 18:05 and 18:10, when a participant selects at 18:10, then selection remains permitted; at 18:15 a new selection is rejected.
6. Given an event crossing midnight, when dated intervals are valid and saved, then stages follow their resolved instants in order rather than comparing time-of-day strings.
7. Given a selection window or quiz whose committed closing time has passed, when an administrator attempts to move it into the future, then saving is rejected with a closed-activity explanation and existing selections/answers/results are retained.
8. Given an event whose end passed while clients and the application were offline, when service resumes and its end is edited into the future, then reopening is rejected, the recap remains default, and valid administrator content corrections still succeed.

## L2-007: Live stage transitions and content

**Traces to:** L1-004

The client must follow the server's current configured stage automatically, including on initial login, refresh, resumed tabs, and reconnection. Administrators must be able to configure timed informational screens and interactive activities within the evening, including multiple screens within a named phase by using consecutive schedule entries. Saved schedule edits must take effect atomically.

Automatic replacement applies to the main event screen. Browsing another core activity must preserve the participant's view and draft while announcing and linking to the new current stage. Each timed entry has its own identity, content, and optional activity reference; two consecutive entries using the same screen type must still display their respective content. Waiting and closing content use the event configuration from L2-001. Screen transitions must not require discarding a draft to access the current activity.

**Acceptance Criteria:**

1. Given a connected participant on the main event screen, when a stage starts or an administrator changes the valid current schedule, then its screen appears within two seconds without a reload.
2. Given a suspended tab or disconnected participant who missed three stages, when authentication and synchronization succeed, then the current activity is restored under the measurement convention without replaying missed activities or animations; a separately browsed core activity follows criterion 4.
3. Given unsubmitted profile or message text, when the scheduled screen changes, then that draft remains available in the same browser session; a quiz closing does not submit an unanswered question automatically.
4. Given a participant viewing profiles, chat, or project details, when a stage changes, then the client announces the current activity and makes it accessible immediately; returning to the event screen shows the current stage rather than a stale one.
5. Given adjacent informational entries of the same screen type, when their boundary is reached, then the second entry's title, content, and links replace the first entry's within two seconds.

## L2-009: Participant-selected teams

**Traces to:** L1-005

Administrators must configure team names and the random or participant-selected assignment mode. In participant-selected mode, active participants must join, leave, or switch among configured teams during the selection stage. There is no team capacity limit in this version. Administrators must be able to correct assignments after selection closes.

A membership change must never move the old team's project selection or build links with the participant; the participant acquires their new team's existing selection and permitted link editing. Administrator corrections must explicitly select affected participants and teams, preserve one membership per participant, and show the resulting assignments before save. Team removal must be rejected while memberships, a selected project, or a demo slot still reference it; administrators must explicitly clear/reassign those dependencies first. Removal from choices must preserve retained historical identities and build entries.

**Acceptance Criteria:**

1. Given an open selection stage in participant-selected mode, when an unassigned participant joins a team, then that team and its membership are displayed and the participant has exactly one membership.
2. Given a participant already on team A, when they switch to B, then the change removes A membership and adds B membership atomically; leaving instead makes them unassigned.
3. Given concurrent join/switch requests, when processed, then the participant ends with at most one team and clients show the saved assignment.
4. Given random mode or a closed selection stage, when a participant attempts to change membership, then the change is denied with an explanation; an administrator can still correct the assignment without altering quiz or raffle history.
5. Given a participant moving from team A to B, when the change succeeds, then A's selection and links remain unchanged and the participant sees B's selection; an unassigned participant receives no team-link editing permission.
6. Given a team with members, a selected project, or a scheduled demo, when removal is attempted, then the dependencies are identified and removal is rejected without changing them.

## L2-010: Balanced random assignment

**Traces to:** L1-005

In random mode, an administrator must trigger assignment of all active roster entries, including those not yet signed in, across configured teams. A fresh assignment must shuffle participants and produce team counts differing by at most one. Later newly added participants must be assigned to a smallest team when the administrator requests assignment of unassigned entries; existing assignments remain unchanged.

The interface must distinguish a fresh full reassignment from assignment of unassigned entries. Full reassignment requires confirmation of the preview and replaces active memberships only; inactive retained memberships do not participate in balancing. A preview must be saved unchanged unless its roster/team version is stale, in which case it must be regenerated for review. Changing the configured assignment mode alone must not reshuffle memberships. After selection closes, full random reassignment remains an explicit administrator correction rather than a reopened participant action.

**Acceptance Criteria:**

1. Given ten active participants and three empty teams, when random assignment runs, then all ten are assigned exactly once with team counts 4, 3, and 3 in some order.
2. Given existing assignments and two newly added participants, when unassigned entries are assigned, then existing memberships are preserved and each new participant joins a currently smallest team.
3. Given no teams or no eligible unassigned entries, when assignment is requested, then an actionable empty-state message is shown and no existing membership changes.
4. Given a repeated request after its response was lost, when retried, then saved assignments are returned without reshuffling participants.
5. Given existing memberships and a changed assignment mode, when that setting alone is saved, then memberships are unchanged; cancelling a full-reassignment preview also preserves them.

## L2-011: Project choices and proposals

**Traces to:** L1-005

Administrators must configure either predefined-only project selection or a mode also allowing participant proposals. Projects must have a title and description; accepted proposals must immediately become event choices without a separate approval workflow. One project can be selected by multiple teams; each team has at most one selected project. Any team member can select or change its project during selection.

Submitting a proposal does not select it automatically and does not require team membership. Proposal creation requires an open selection window; once accepted, it becomes an event-owned choice editable/removable by administrators under L2-012, not by its proposer. Disabling new proposals must preserve previously accepted choices and selections; predefined-only thereafter means selecting from the existing administrator-managed catalog without adding proposals. An administrator can clear or correct a team's selection after closing, with link retention under L2-024.

**Acceptance Criteria:**

1. Given predefined-only mode, when participants view choices, then the existing event catalog remains available; when a new proposal is submitted directly, then it is denied without adding a choice or changing a selection.
2. Given proposals enabled and selection open, when a participant submits a nonblank title and description, then the project becomes visible to the event and can be selected without a Liturgy URL or account.
3. Given a team member selecting a project, when the save succeeds, then every team member sees that one selected project; a concurrent stale selection is rejected and refreshed rather than silently replacing a newer selection.
4. Given an unassigned participant, a project from another event, or closed selection, when a team project selection is attempted, then the change is denied; administrators can correct the selection afterward.
5. Given a previously accepted proposal already selected by a team, when an administrator disables new proposals, then the choice and team selection remain and further proposals are denied.

## L2-012: Project details and building guidance

**Traces to:** L1-005

Project-selection and project-detail screens must show configured descriptions, selected teams, building guidance, and available repository/demo links. Administrators must customize guidance and tools links without requiring project-management features in this platform.

**Acceptance Criteria:**

1. Given a selected project with guidance and build-tool links, when a team views its details during Develop, then that guidance and the configured links remain available independently of Use Liturgy.
2. Given no selected project or no configured projects, when the participant opens project details or choices, then an explanatory empty state identifies the next allowed action rather than showing a broken page.
3. Given an administrator editing guidance, when the save succeeds, then participants receive the updated text without losing team membership or selected projects.
4. Given a project selected by a team, when its removal is attempted, then removal is rejected until administrators explicitly reassign or clear the affected selections.

## L2-013: Participant profiles

**Traces to:** L1-006

Participants must edit an event-specific profile containing an optional biography, skills, interests, and looking-for-help tags. The roster name identifies the participant. Profile sharing must default off; choosing to share makes those fields visible only to authenticated participants in that event. Email must never become a public profile field.

The profile editor must display the roster name read-only; name corrections use administrator roster editing. Saving optional details must not implicitly enable sharing. Turning sharing off must retain the owner's saved fields for later editing while removing them from all other participants' profile/directory/recommendation views within the connected-update deadline. Clearing a field must remove its saved value. No synthetic role, biography, or interest can substitute for absent participant input.

**Acceptance Criteria:**

1. Given a participant with no optional fields, when they skip profile creation, then every other core event feature remains available.
2. Given a profile owner, when they save shared profile fields, then same-event participants can view them; participants in other events cannot.
3. Given a shared profile, when the owner disables sharing or clears a field, then subsequent profile reads and recommendations no longer expose that content.
4. Given another participant's profile, when a participant attempts to edit it, then the server denies the change and the saved profile is unchanged.
5. Given a new private profile, when its owner saves optional fields without enabling sharing, then only the owner can read them; enabling and then disabling sharing retains the owner's fields while removing them from other participants' views.

## L2-014: Explainable people recommendations

**Traces to:** L1-006

Recommendations must rank other active, sharing participants in the same event by the number of distinct shared normalized tags across skills, interests, and help tags. Normalization trims whitespace and ignores case. Return at most five matches, exclude self and blocked participants in either direction, and break equal scores by display name then stable participant identity. No external AI service is required.

Both the requesting participant and candidate must have sharing enabled. Compare the union of all three tag categories, so the same normalized tag contributes once even across different categories. Use the directory's case-insensitive display-name ordering for equal scores. Explanations must list only the actual intersecting tags, not the candidate's entire interests list or inferred similarities.

**Acceptance Criteria:**

1. Given candidates sharing three, two, and zero tags, when recommendations load, then the three-tag candidate precedes the two-tag candidate and the zero-tag candidate is excluded, with shared tags explaining each result.
2. Given repeated or differently cased versions of the same tag, when scores are calculated, then that tag contributes one match only.
3. Given no shared tags, no shared profile, or no eligible candidates, when recommendations load, then the client explains that no matches are available without inventing similarities.
4. Given a profile becoming private or a block being added, when recommendations refresh, then the affected candidate is absent; profiles from another event never enter the candidate set.
5. Given six eligible candidates with identical match counts, when recommendations load, then the first five by display name/stable identity appear with their actual shared tags; repeated loads of unchanged data preserve that order.

## L2-015: Private participant chat

**Traces to:** L1-006

Active participants must exchange persistent, text-only, one-to-one messages with other active participants in the same event. Messages must contain 1-2,000 characters after trimming. Conversations must show sender, server timestamp, chronological order, and sending/sent/failed state. Attachments, group chat, and cross-event conversations are outside this version.

Conversation history must be readable by its authorized parties even if the other entry becomes inactive; new sends then fail with an unavailable-recipient explanation and retain the draft. A conversation must be identified by both participant identities and event, never by recipient alone or display name. Server timestamps must display a date and time in the event timezone; equal timestamps use server-assigned message order. Sent means durable acceptance, not a read receipt. No message editing, deletion, attachment, or read-receipt feature is required.

**Acceptance Criteria:**

1. Given two unblocked same-event participants, when a message is accepted, then both can see it within two seconds while connected and can read the saved conversation after refresh.
2. Given a blank message, a message over 2,000 characters, self-recipient, or other-event recipient, when sent, then it is rejected without adding a conversation message.
3. Given a lost response after a message was saved, when the sender retries that send, then exactly one message appears; two intentionally separate sends with identical text remain two messages.
4. Given a disconnected sender, when sending fails, then the draft and failed state remain visible with an explicit retry action; the client does not claim delivery or silently send the draft on reconnection.
5. Given A/B and C/B conversations in the same event, when A opens their B conversation, then only A/B messages appear, including after refresh; C/B messages remain inaccessible.

## L2-016: Blocking, reporting, and moderation

**Traces to:** L1-006

Participants must block or unblock another participant and report a specific received message with an optional reason. Either-direction blocking must prevent new messages between the pair and exclude recommendations, without deleting history. Administrators must review reports with the reported message and reason and resolve them or deactivate an abusive participant; ordinary chat history is not an administrator browsing feature.

A report must retain the reported message, its sender/recipient identities, server timestamp, and the optional reason at submission. Reasons and resolution notes are optional plain text limited to 5,000 characters. A participant must be able to report retained received history even while blocked. One report per reporter/message is sufficient: repeat submissions return that report without duplication. Admin report review must list pending and resolved reports and show only the reported message and related report fields, not neighboring messages. Resolution must record an outcome (resolved without action or participant deactivated), optional note, administrator, and time. Reporting must neither notify the reported participant of the reporter's identity nor automatically block/deactivate anyone.

**Acceptance Criteria:**

1. Given A blocks B, when either attempts a new message to the other, then delivery is denied; existing conversation history remains visible to its parties.
2. Given A removes their block and no reverse block exists, when either sends a valid message, then delivery succeeds again.
3. Given a received message, when its recipient reports it, then a report is saved for administrator review; reporting an inaccessible message is denied and retrying the same report does not duplicate it.
4. Given an administrator resolving a report, when a resolution is saved or the reported participant is deactivated, then the outcome is recorded and deactivation immediately prevents subsequent authenticated actions.
5. Given a retained received message in a blocked conversation, when its recipient reports it twice, then one pending report with the submitted message/reason is available to administrators and unrelated conversation contents remain inaccessible to them.
6. Given a pending report, when an administrator resolves it without deactivation, then it appears as resolved with the actor/time/outcome and no participant access change; cancelling resolution leaves it pending.

## L2-017: Quiz configuration and lifecycle

**Traces to:** L1-007

Administrators must create event quizzes with an ordered set of single-choice questions, each with 2-6 nonblank options and exactly one correct option. Quizzes must have explicit opening and closing times within the event; the quiz stage must expose the active quiz. Questions and answer keys must become immutable once the quiz opens.

Each quiz must have an event-local identity and title. Administrators must be able to save an incomplete inactive draft, add/remove/reorder its questions, and explicitly activate it after validation. An activated quiz opens at its inclusive opening instant and closes at its exclusive closing instant. Activation must occur before opening. Activated quiz windows must not overlap within an event. A published quiz screen entry must reference one activated quiz in the same event and fit within its answer window; activating the quiz and linking its stage must be saveable atomically. An event draft may reference its inactive quizzes, but publication must reject such references until valid activation. Navigation lists activated quizzes as upcoming, open, or closed; inactive drafts are administrator-only. Opening time, questions, order, and answer keys are fixed once opening occurs; closing-time changes must obey L2-006's closure rules. Quiz removal/deactivation is permitted only before opening, with affected screen references explicitly removed or reassigned in the same save; an opened quiz cannot be removed, reset, or deactivated to bypass closure/history rules.

**Acceptance Criteria:**

1. Given a missing quiz title, empty quiz, blank question, invalid option count, or missing/multiple correct options, when activation is requested, then validation identifies the issue and the quiz remains inactive.
2. Given a valid scheduled quiz, when its opening time arrives, then participants can answer; at the closing instant new answers are rejected and results become available.
3. Given a quiz already open or with submissions, when an administrator tries to alter questions or correct answers, then the edit is rejected without affecting saved answers.
4. Given a participant requesting quiz content before closing, when the server responds, then no correct-option metadata or other participants' answers are disclosed.
5. Given an inactive incomplete quiz, when it is saved, then it remains editable and invisible to participants; attempting activation with invalid questions, overlapping times, or an invalid stage reference returns specific errors without partial activation.
6. Given quizzes A and B at separate times, when their referenced stage entries become current, then each opens the correct quiz; submissions and results for A never appear as B's data.
7. Given an activated upcoming quiz, when a participant opens it before its opening time, then its title and opening time appear without an enabled answer action; an empty quiz list explains that none are scheduled.
8. Given a copied event draft referencing inactive quizzes, when publication is requested, then the referenced quizzes are identified and publication fails until they are validly activated or the screen references are removed.

## L2-018: Quiz answer submission

**Traces to:** L1-007

Each participant must submit at most one answer per question while its quiz is open. The server's receipt time determines eligibility; viewing a question earlier does not reserve a submission. Confirmed answers must be immutable and persist across refresh.

Participants must navigate questions in their configured order and be able to revisit or skip questions while open. Submission feedback must confirm only the saved choice, never correctness or score before closing. After the last question, show submission progress and closing time until results are available. Refresh must restore saved choices; returning to an answered question must not enable replacing its answer. A participant cannot reset submissions or restart for another score.

**Acceptance Criteria:**

1. Given an open quiz and an unanswered question, when a valid option is submitted, then one answer is saved and shown as submitted after refresh.
2. Given an existing answer, when a different option is submitted or two different answers arrive concurrently, then at most one answer is accepted and the saved answer is returned with an explanation.
3. Given an exact retry of an accepted answer, when processed, then it returns the saved submission without awarding additional points.
4. Given a not-yet-open or closed quiz, or an option belonging to another question or event, when a new answer is submitted, then no answer is saved and the participant sees a denial without private foreign-resource details; an exact retry of an already committed answer follows L2-044.
5. Given an accepted choice while the quiz remains open, when its confirmation appears or the question is revisited, then the saved choice is shown without correctness, points, or an enabled replacement action.
6. Given skipped questions and a still-open quiz, when the participant navigates back, then unanswered questions remain available; reaching the last question does not close the quiz or reveal results.

## L2-019: Quiz scoring and results

**Traces to:** L1-007

Leaderboards include participants with at least one submitted answer to that quiz and use competition ranking: 1, 1, 3 for a two-way first-place tie. No aggregate cross-quiz score is required. Equal-rank rows use the directory's name/identity ordering for display only. Participants with no answers see a personal zero score but do not enter the leaderboard.

**Acceptance Criteria:**

1. Given two correct, one incorrect, and one unanswered question, when the quiz closes, then the participant's result is 2 out of 4 and identifies each answer's outcome.
2. Given participant totals 3, 3, and 2, when results load, then their ranks are 1, 1, and 3; equal scores are never broken by response speed.
3. Given a closed quiz, when its result screen is refreshed or revisited, then scores remain unchanged and other participants' email addresses and individual answer histories remain private.
4. Given a participant with no answers and a quiz with no submissions, when it closes, then the personal result shows zero out of the question count with unanswered outcomes and the leaderboard shows an explicit no-submissions state.

## L2-042: Abuse limits and actionable denials

**Traces to:** L1-013

Authentication must allow at most ten failed attempts per source address per rolling five minutes and five per submitted code verifier per rolling five minutes. Failed admin sign-ins must also use the address limit and a five-failure account limit. Chat sends must allow at most 30 accepted messages per sender per rolling minute. Limits must persist across application instances; denials must be generic for authentication and must not permanently lock an account.

Failure counters must be keyed consistently for normalized identities, including nonexistent ones, without retaining plaintext secrets. Either exhausted authentication counter denies the next attempt; throttled attempts do not extend the window by counting as newly tested failures. Denials must supply a positive retry delay in seconds. An exact retry returning an already accepted message does not consume another chat allowance; a distinct intentional send does.

**Acceptance Criteria:**

1. Given the relevant failed-login limit has been reached, when the next attempt arrives before the window expires, then it is rejected with a retry delay without testing or revealing the credential's validity.
2. Given 30 accepted messages within a minute, when the sender attempts a 31st, then it is refused with a retry delay and retained as an unsent draft; another sender's allowance is unaffected.
3. Given the limiting window has elapsed, when a valid request is repeated, then normal processing resumes without administrator intervention.
4. Given authentication attempts using nonexistent and existing identities with wrong credentials, when responses are compared, then neither response exposes whether a roster binding or administrator account exists.
5. Given five tested failures for one code within five minutes from otherwise unthrottled addresses, when a sixth attempt arrives, then it is denied before credential testing; after those failures age out, a valid attempt can succeed.

## L2-044: Persistence, interruption, and recovery

**Traces to:** L1-014

**Acceptance Criteria:**

5. Given a documented database backup from a test event, when restored into an isolated environment, then saved registrations, selections, messages, quiz results, and raffle history from the backup are readable and coherent; the runbook states backup frequency and recovery steps.
6. Given an accepted quiz answer or message whose response was lost, when the authorized requester repeats its original operation after the window closes or connectivity returns, then the saved outcome is returned once; changed input under the same identity is rejected.
7. Given a stale team-link edit, when newer authorized values are returned, then the editor's unsaved values remain available for explicit reapplication against the refreshed version and no newer values are overwritten automatically.

## L2-058: Atomic changes, concurrency, and interruption recovery

**Traces to:** L1-014

6. ## L2-059: Attributable outcomes and usable command results

**Traces to:** L1-014

CLI operations must produce attributable records with operation identity, authenticated database principal when authentication succeeded, resolved target, UTC time, action, duration, and outcome; event/subject identifiers and available affected-row counts must be included when known. Operator identity must not be an unverified free-text actor argument. Validated successful mutations must persist their audit/receipt under L2-058. A local durable operation journal must record attempts and outcomes, including a started SQL execution before sending its script; if that initial record cannot be written, execution must not begin. After interruption, an unfinished journal entry means unconfirmed, not success. These records are not claimed to be tamper-proof against the machine/database operator.

Diagnostics and audit records must follow L2-045 exclusions and must not contain raw SQL, seed contents, result rows, or credential values. Explicit previews, roster/query results, and requested exports are operator data output, not diagnostic logs; sensitive results must not be copied automatically into logs. Local journals and preview/export artifacts must use access restricted to the operator by default. The tool must report an output/export failure after commit as a delivery failure with the committed outcome retained, never as a failed mutation to be replayed.

Commands must offer readable text and a structured JSON result with operation ID, target, outcome, duration, result data when requested, and a redacted error code/message when applicable. JSON mode must keep progress/diagnostics off stdout and represent SQL result sets without silently dropping rows; failure after streamed/partial output must be identifiable. Exit codes must be stable: 0 successful completion (including preview or reconciled success), 1 confirmed execution failure or known partial completion, 2 syntax/configuration/validation error, 3 authentication/authorization denial, 4 stale input or operation conflict, 5 cancellation before execution or confirmed rollback on cancellation, 6 unconfirmed database outcome, and 7 committed operation with failed result delivery. Outcomes must distinguish cases sharing an exit code.

**Acceptance Criteria:**

## L2-062: Reset administrator passwords atomically

**Traces to:** L1-016

The CLI shall offer `reset-password [<username> | --all] [--prompt-password | --password-stdin]`, requiring exactly one selector and one password option. A reset shall validate and hash the password through Identity, refresh security/concurrency stamps, and revoke existing administrator sessions in the same transaction. Bulk reset shall include disabled and role-revoked administrator accounts without changing their enabled status, roles, identity, or history. Participant entry codes shall remain unchanged. Bulk reset shall commit all selected changes or none. Successful output shall identify affected usernames and count without credentials. Empty bulk selection shall succeed with count zero. Unknown usernames shall fail without implicit creation.

**Acceptance Criteria:**

1. Given a signed-in administrator, when its password is reset, then its old session and old password fail, the new password succeeds, and another account remains unchanged.
2. Given enabled, disabled, and role-revoked accounts, when all passwords are reset, then every selected password hash changes, all their sessions are revoked, and roles, enabled flags, identities, and participant credentials remain unchanged.
3. Given invalid input, a database failure during a later account update, or a concurrency conflict, when a reset fails, then no selected password or session changes are committed.
4. Given no accounts, when all passwords are reset with valid input, then the command succeeds with zero affected accounts; a named missing account fails.
5. Given conflicting or missing selectors/password options or canceled/empty input, when reset is attempted, then it fails without changing accounts.
6. Given an uncertain commit or result-delivery failure, when reporting finishes, then the command does not claim rollback or repeat the mutation automatically; confirmed success lists only affected usernames and count.

The September 8 account-command increment explicitly uses the existing `ConnectionStrings:EventDatabase` configuration and database grants. For add-user and reset-password, this supersedes the named-target, preview/apply, durable receipt/journal, and structured-result requirements of L2-050 and L2-057 through L2-059. These account commands shall use protected operator connection configuration, report the resolved server/database and principal before mutation, and never change Azure firewall rules or elevate database grants. Command-line password values shall remain prohibited. SQL/connection errors shall be redacted; uncertain outcomes shall return a nonzero result and require inspection before retry.
