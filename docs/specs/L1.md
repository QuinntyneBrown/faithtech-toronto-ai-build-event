# L1 - High-Level Requirements

## Basis and complete scope replacement

The September 9, 2026 product direction in [the brief](../prompt.md) supersedes all previous platform requirements. [The run sheet](../run-sheet.html) supplies event context, including RTR's meaning and the introduction prompts; its operational instructions are not additional app features. The PowerPoint remains the presentation, with the companion supporting four interactive moments.

Deliver **one Angular application with exactly four screens: Countdown → Projects → Team selection → Raffle**, a .NET API with SignalR, and a passcode-management CLI. Administrator login and tools belong within these screens. No separate admin application, design-system site, slide player, or extra activity screen is required. All UI is consumed from `@quinntyne/cornerstone` on npm; missing UI is completed in Cornerstone and adopted through a released version.

This is a requirements revision, not a claim that existing code satisfies it. Retained IDs keep their capability lineage but their text is replaced to match the new direction. Removed IDs are not reused or renumbered; gaps are deliberate. New L2 IDs begin at L2-063, after the previous highest ID.

## L1-001: Participant administration
Administrators must view, add, update, and delete participants directly on Countdown, including correcting the roster after the public screen has advanced.

## L1-002: Email entry
Participants must enter using only an email address, receive confirmation of raffle entry, and retain their entry in the same browser without duplicate registration or disclosure of another person's private information.

## L1-003: Countdown and welcome
Countdown must welcome participants, show brief event information and the remaining time, and keep entry available until an administrator closes the screen.

## L1-004: Four-screen presenter-controlled flow
The application must follow the administrator's current screen across connected browsers and recover that screen after interruption. The presenter must control progression independently of the PowerPoint and clock.

## L1-005: Projects and teams
Participants must see RTR project cards and randomly formed three-person teams. Administrators must manage projects, rearrange team members, and assign projects to teams within the appropriate screens.

## L1-006: Optional personal information
After email entry, participants must be able to supply their name, what they make, and what is on their heart without making those details a condition of participation or raffle eligibility.

## L1-008: Live raffle
Administrators must draw a random participant with animated name cycling and a falling-particle winner celebration. Every connected viewer must see the same durable result, and presentation effects must never determine or change the winner.

## L1-011: Cornerstone UI delivery
The entire application UI must use the published Cornerstone package. Missing UI capabilities must be implemented, tested, and released in Cornerstone before the application consumes them, preserving a consistent light-theme experience.

## L1-012: Accessible and responsive experience
All four screens and inline administrator tools must work from small phones through projected desktop views, with keyboard operation, readable feedback, and usable motion and GPU fallbacks.

## L1-013: Administrator access and data protection
A shared four-digit passcode must enable administrator capabilities while keeping participant entry email-only. Security hardening, privacy enforcement, abuse protection, and protected database-operator input are **NON-MVP**; their retained L2 requirements document possible later work and do not block MVP completion.

## L1-014: Realtime reliability and operations
The application must synchronize state through SignalR, meet measurable live-event performance targets, preserve ordinary sequential changes, and provide readiness and recovery instructions. Concurrency/race/idempotency guarantees, mutation auditing, correlated diagnostics, and security redaction are **NON-MVP**.

## L1-015: Installable passcode tool
The solution must include a CLI that can be installed and updated on the operator's Windows machine and used against an explicitly selected database with its existing database permissions.

## L1-016: Replace the shared administrator passcode
Anyone with the required database access must be able to replace the shared four-digit passcode directly in the database or with the supplied CLI. Replacement must take effect without redeployment and invalidate previously established administrator sessions.

## Explicit exclusions and defaults

The former multi-event administration, publication, timed stage engine, individual entry codes, account/password administration, participant-directed selection/proposals, messaging, recommendations, quizzes, prize catalogue, demo management, showcase/recap, venue map, Liturgy connection, standalone design system, and general SQL/admin tool suite are removed. Retired L1 IDs are L1-007, L1-009, L1-010, and L1-017; their former L2 obligations are removed. Historical mocks, tests, and deployment/design documents do not add them back.

Specification defaults, distinct from the user's explicit requirements: countdown to the 17:20 welcome; manual forward progression; public entry closes with Countdown; uniform random grouping with a final remainder team; unrestricted administrator corrections of team sizes; private optional answers; public participant labels without emails; no repeat raffle winners. The run sheet's 2–3-person seating and low-turnout pairs are handled through manual moves, not an additional grouping mode. No profile-based matching is inferred from the unfinished phrase “randomly formed based”. Security, abuse protection, auditing, and concurrency-safety defaults are retained only as explicitly marked **NON-MVP** future work.

## Implementation and acceptance conventions

[AGENTS.md](../../AGENTS.md) supplies implementation constraints: Angular with signals, interface/InjectionToken service consumption and separate template/style/class files; .NET Clean Architecture, vertical slices, MediatR pinned to 12.5.0, and Microsoft.Extensions patterns. HTTP and SignalR adapters belong in `api`; consumers inject service contracts. The CLI uses System.CommandLine, a project under `backend/src`, .NET tool packaging, and a local build/package/install-or-update script under `eng/scripts`.

Implement one thin slice at a time: select L2 criteria, write a failing behavioral acceptance test, implement, verify, and commit. API integration acceptance uses the real API and disposable persistence under `backend/tests`; CLI acceptance invokes the packaged executable and verifies subsequent API behavior. Playwright tests use one page object per screen under `e2e/page-objects`, with selectors and interactions confined to those page objects, and tests under `e2e/specs`. Inject mock service contracts for Playwright; those tests never call production adapters. Separate API/SignalR integration and load checks establish real delivery.

Every acceptance-test file must include a comment header: `// Acceptance Test`, `// Traces to: L2-003` (its actual IDs), and `// Description: ...` (the behavior). Traceability, package provenance, type placement, and repository layout are reviewed, never enforced by architecture tests or tests that parse these specifications. Documentation completion does not require inventing failing application tests before implementation begins.
