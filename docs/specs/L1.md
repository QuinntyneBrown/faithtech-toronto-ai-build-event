# L1 - High-Level Requirements

## Basis and scope

The authoritative product input is [docs/prompt.md](../prompt.md), subject to later explicit user decisions. These requirements incorporate the scope and defaults confirmed during planning on September 7, 2026. The [presentation source](../build_deck.py) supplies the configurable September 9 reference schedule; it does not override the product scope or confirmed Cornerstone light reference. The [five-pass review](REVIEW.md) records corrections and distinguishes user decisions from additional specification defaults. Mock behavior and its coverage claims do not supersede requirements.

The deliverable comprises an event participant client, an administration application, an independent design-system site, and a locally installed operator CLI. All capabilities below are first-version scope. Ongoing project management, Liturgy API integration, shared sign-in, automatic workspace invitations, and publishing or adopting Cornerstone are outside this version.

## L1-001: Event administration

The system must let users with the admin role configure independent, reusable events, participant rosters, content, links, activity settings, venue information, and branding.

## L1-002: Participant access

The system must let registered participants access their event using an email address and an individual entry code, preserve their identity across visits, and support administrator-controlled access recovery and revocation.

## L1-003: Countdown and venue

Before an event starts, the client must display a countdown, configurable venue logo, and location map, and must open the live experience automatically at the configured start time.

## L1-004: Scheduled event flow

The system must automatically display the current configured stage and activity, follow authoritative event time, and restore the correct screen after interruption. Event timing must remain independent of project progress.

## L1-005: Teams and projects

The system must support random or participant-selected teams, administrator-predefined or participant-proposed projects, project selection and details, and building guidance using participants' chosen tools.

## L1-006: Profiles, networking, and messaging

Participants must be able to share optional profile information, receive explainable recommendations of people to meet, and exchange private messages with other participants in their event, with blocking and reporting controls.

## L1-007: Quizzes

Administrators must be able to configure and run event quizzes, collect participant answers, and reveal scores and results consistently.

## L1-008: Raffles and prizes

Administrators must be able to configure prizes and run fair, persistent raffle draws with cycling participant names, WebGPU visuals, playful audio, and winner celebrations. Winners must be excluded from subsequent draws in that event.

## L1-009: Demonstrations, showcase, and recap

The system must provide an administrator-ordered demo schedule and a participant-accessible project showcase and recap containing repository and demo links after the event.

## L1-010: Optional Liturgy connection

Each event must support an optional, default-disabled Liturgy link experience while remaining independently usable. Disabling integration must preserve configured links and hide all participant-facing Liturgy content. The September 9 reference event must have integration disabled.

## L1-011: Independent matching design system

The platform must own a standalone design system that matches the recorded Cornerstone light-theme primitives and their behavior, supplies authoritative local tokens, and works independently of the Cornerstone and Liturgy repositories and deployments. All mockups and production interfaces must follow it regardless of integration settings; event compositions must preserve the light-only experience.

## L1-012: Responsive and accessible browser experience

The client, administration interface, and design-system site must remain usable from mobile through desktop in the latest stable Google Chrome, with keyboard access, readable light-theme states, accessible feedback, and appropriate motion and sound alternatives.

## L1-013: Security and participant information

The system must authenticate administrators and participants, enforce roles and event boundaries on the server, validate untrusted input, protect credentials and private information, and prevent unauthorized access and changes.

The local operator CLI must authenticate through an authorized database identity, protect its credentials, and distinguish database operator authority from browser administration. Administrator account commands may use the application's existing database connection when its grants permit the operation; a separate provisioner login is not required for account creation, disabling, or password resets.

## L1-014: Performance, reliability, and operations

The system must meet measurable response and live-update targets, preserve acknowledged actions across service restarts, recover from interrupted connections without duplicate outcomes, and expose operational diagnostics without leaking participant information.

Production CLI writes must require preview and explicit apply, attributable outcomes, and interruption recovery. Validated operations must preserve atomicity and reject stale updates; arbitrary SQL must expose its different transaction and retry guarantees.

## L1-015: Local operator tooling

The system must provide an installable, updateable CLI that an operator can run on their Windows machine against explicitly selected databases, including the deployed production Azure SQL database, with identifiable targets and actionable connection failures.

## L1-016: Validated data administration

The CLI must manage event configuration, schedules, publication, rosters, credentials, and administrator accounts through validated operations, and import event seed files without unintended duplication or loss of participant and activity data.

## L1-017: Advanced data repair

The CLI must let an authorized database operator inspect and change any application data through supplied SQL, including bulk updates and deletion beyond ordinary application rules, subject to database permissions and constraints.

## Approved defaults

- Access: an individual code identifies a roster entry; first successful access binds the supplied email. An entry code is an access credential, not proof of email ownership.
- Timing: server-authoritative time, nonoverlapping stages, waiting content during gaps, recap after closing, and current-stage recovery on reconnect.
- Participation: one team per participant, one selected project per team, balanced random assignment, participant changes during selection, administrator corrections afterward.
- Quizzes: single-choice questions, one submission per question, one point per correct answer, results after closing, equal ranks for ties.
- Networking: optional skills, interests, and help tags; recommendations based on shared tags; private same-event text chat with blocking and reporting.
- Raffles: participants who accessed the event are eligible; prior winners are excluded; results persist before animation; retries cannot select another winner.
- Demos: administrators order slots, teams supply repository and demo URLs, and participants retain showcase and recap access after closing.
- Baseline: 200 concurrent participants, API p95 at or below one second, and connected stage transitions within two seconds.
- Reference event: September 9, 2026, 17:00-21:00 America/Toronto, Stone Church; no inferred venue address. Detailed requirements define the preset.

Additional explicit decisions confirmed during this review:

- Visual reference: retain Cornerstone light styling and the authoritative local `--cs-*` prefix, superseding the interim Liturgy reference and `--ft-*` prefix.
- Closure: schedule edits cannot reopen closed quizzes or team/project selection; explicitly authorized administrator corrections remain available.
- Build ownership: retain repository/demo links for each event/team/project pairing; switching selects that pairing's saved links, initially blank.

CLI decisions confirmed on September 8, 2026: extend the existing provisioning tool; Super admin means an authorized database operator, not a new web role or a required web login. Administrator account commands may reuse the application's database connection and existing grants. SQL authentication remains supported by the existing deployment configuration. Local Windows execution is required; macOS support is not inferred from "my machine."

Dedicated validated commands cover event configuration, schedules, publication, roster/credentials, administrator accounts, and existing migrations. Dedicated commands for teams, projects, chat, quizzes, raffles, demos, and recaps are outside this CLI increment. An edited seed updates an explicitly identified event's supplied configuration and schedule while preserving participation data and publication state; seeding does not reset an event.

The operator also has an explicit SQL escape hatch for data outside those commands and exceptional repairs. Production writes use preview then apply, including deliberate scripted approval. General schema/database administration and Azure resource provisioning are outside the new CLI scope; existing application migrations remain supported. SQL execution does not promise automatic repair of application invariants or universal rollback.

CLI detail defaults below make these decisions testable: structured output and exit statuses, finite configurable timeouts, strict import validation, operation identities, and explicit handling of uncertain SQL outcomes. These are specification defaults, not claims about capabilities already implemented or separately selected by the user. The existing deployment guide describes the starting connection/provisioning workflow; L2-060 requires its update when the tool is implemented.

## Implementation and acceptance conventions

[AGENTS.md](../../AGENTS.md) is authoritative implementation guidance: .NET with MediatR pinned to 12.5.0, Microsoft.Extensions patterns, Clean Architecture and vertical slices; Angular sibling admin/client/api/components/domain projects; interface-and-token service consumption; separate component class/template/styles; and a standalone design-system project with its own package, tests, build, and deployment.

These are compiler, formatter, and review constraints, not architecture-test requirements. No new HTTP endpoints are introduced by the CLI requirements; its local file inputs, command results, and exit statuses are specified in L2-049 through L2-060.

Implementation must use incremental implementation and ATDD: select L2 criteria, write a failing behavioral acceptance test, implement and verify the slice, then commit it. API acceptance tests belong under backend/tests. Playwright tests use one page object per screen under e2e/page-objects, with selectors and DOM interactions confined to page objects; tests belong under e2e/specs and use injected mock service contracts instead of production adapters.

Every acceptance test file must include a comment header naming its L2 requirements, for example `// Acceptance Test`, `// Traces to: L2-001`, and `// Description: Verify event configuration`. Documentation coverage and naming constraints must be reviewed; tests must not parse specifications or assert repository structure.

CLI acceptance tests belong under backend/tests and must invoke the packaged executable against disposable SQL databases, verifying observable results through fresh database reads and applicable API requests. Never target production with destructive fixtures. CLI packaging must follow AGENTS.md: System.CommandLine, Microsoft.Extensions dependency injection/logging/Options/Configuration, command-per-file organization, a .NET tool package, and a local build/package/install-or-update script under eng/scripts. These structural constraints are reviewed, not enforced through architecture tests.
